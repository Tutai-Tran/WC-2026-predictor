## The self-learning loop (the model gets smarter over time)

**Goal:** each time a match is played and the dashboard refreshes, an agent should
diagnose *why* a prediction went right or wrong, accumulate the lessons, and feed
statistically-supported corrections back into the algorithm — without a human in the
loop. Designed with multiple agents; built in phases, all wired into `update.py` so it
runs on **every refresh** forever (no Claude session required).

Each refresh now does:

1. **Snapshot (leak-free).** `learn.snapshot_upcoming` freezes the current prediction
   for every still-upcoming match **before** new results are folded into Elo, so the
   post-mortem judges what we predicted *pre-kickoff*, with no current-Elo leakage.
   (Stored in a new `prediction_log` table; `ON CONFLICT … WHERE graded=0` so a frozen
   graded row is never overwritten.)
2. **Grade.** `learn.grade_newly_played` scores each frozen snapshot once the match is
   played (Brier, log loss, correct?), marking wrong ones `postmortem_status='pending'`.
3. **LLM post-mortem.** `learn.run_postmortems` asks the local Claude CLI *why* the
   most-confident wrong picks missed and returns **enum-validated** structured lessons
   (which factor was over/under-weighted, with evidence). A fair upset is tagged
   `variance` and **excluded from learning**, so one shock can't move the model. Stored
   in a `postmortems` table (raw model output kept for audit).
4. **Aggregate.** `learn.aggregate_lessons` projects the graded log + post-mortems into
   leak-free accuracy-over-time, per-segment accuracy, and **ranked systematic biases**.
5. **Obsidian + dashboard.** `memory.write_lessons` regenerates `_memory/LESSONS.md`
   (the curated "what the model has learned" note), and the dashboard's new
   **🧠 Learning tab** surfaces it all.
6. **Candidate nudges (phase 3a).** `learn.propose_adjustments` turns a bias into a
   **candidate** parameter nudge only once **≥8 distinct wrong matches** tagged that
   factor (systematic, not anecdote) and only where it maps to a real fitted knob
   (goal_scale, c, home_adv_elo, rho). Candidates are written to
   `data/raw/learned_adjustments.json` (gitignored, audit-only) and are **never
   auto-applied**.

### Why parameters don't change during the tournament (key decision)
Agents proved with numbers that learning from a *single tournament* chases noise — the
per-match sampling error is larger than the real signal, which is exactly how the
earlier flat `goal_scale=1.10` **overfit** and hurt over/under accuracy out-of-sample
(54.7% → 48.6%). So: **"the LLM proposes hypotheses, the math disposes."** During the
tournament the live self-improvement is (a) the **Elo updating from every result**
(already happening) and (b) the **accumulating lessons**. Actually *applying* a
parameter change is gated behind **phase 3b — the out-of-sample validated re-fit gate**
(re-fit on rolling origin, adopt only if it beats the incumbent, with rollback). 3b is
deliberately **deferred / frozen** until enough new matches accumulate to validate a
change safely. This is the statistically correct behaviour, not a limitation. Exact-
score accuracy stays inherently ~10% (Poisson); the learnable wins are calibration and
systematic-bias correction.

### Leak-free guarantee
Confirmed by a review agent via two orthogonal guards: the snapshot reads the *previous*
forecast payload (pre-result), and the `ON CONFLICT … WHERE graded=0` freeze. So the
"why were we wrong" analysis can never see information from after kickoff.

## Live crash fix (end of session)

The live site started throwing a redacted `sqlite3.DatabaseError` at
`app.py:load_latest → conn.execute(...)`. Diagnosis: the published artifact itself was
**fine** (validated: quick_check ok, 17 forecast rows); the bug was **entirely
cloud-side** in the DB sync, two root causes:

1. `_sync_remote_db` wrote the raw HTTP body straight over `wc26.db` with **no
   validation** — a partial download or an HTML 404/redirect served during the
   `gh release upload --clobber` republish window got swapped in as a "database".
2. `connect()` forces `journal_mode=WAL`, so a prior connection leaves
   `wc26.db-wal`/`-shm`; the swap replaced only the **main** file, leaving **stale
   sidecars** that, read against the new file, raise *"database disk image is
   malformed"*.

**Fix** (commit `973bf74`):
- `db.is_valid_snapshot()` — SQLite magic header + read-only `quick_check` + a forecast
  row must all pass before install.
- `db.install_snapshot()` — validate → clear stale `-wal`/`-shm` → atomic `os.replace`;
  a rejected download leaves the existing DB untouched.
- `load_latest()` and the tab connections now catch `sqlite3.Error` (+ bad payload),
  **self-heal** the disposable hosted DB (delete + force clean re-sync), and show a
  friendly waiting state instead of crashing the page.
- 7 new tests + a real-bytes integration sim.

Note: an adversarial reviewer claimed `OperationalError` escapes `DatabaseError`; I
verified directly that in CPython it's a **subclass**, so the original catch already
covered it — broadening to `sqlite3.Error` and guarding `json.loads` are still genuine
improvements. (Lesson: verify review claims against the runtime, don't trust blindly.)
